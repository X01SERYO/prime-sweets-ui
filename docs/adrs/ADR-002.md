# ADR-002 — Extend the existing seller modules

**Status:** Proposed
**Date:** 2026-10-31
**Document role:** Architecture decision for the UI feature in [PDR-002](../pdrs/PDR-002.md). Not a description of the running UI.
**Depends on:** [ADR-001](./ADR-001.md) and the API [ADR-002](../../../prime-sweets-api/docs/adrs/ADR-002.md).

## Context

The seller will see the current week, set a delivery date before the lines, read a Load Sheet by delivery date, and correct or void a sale from that date. The API remains authoritative. Catalog Excel import and Alegra sync stay on the API.

## Decision

No new feature module and no new route tree for "returns".

| UI behavior | Module |
|---|---|
| Current-week list | `sales-day` |
| Delivery date question, line edits, void | `sales` |
| Sales for one delivery date, Load Sheet for that date | `fulfillment-output` |

`SetSaleDeliveryDate` is a use case in `sales`. It calls the API. It does not decide the week. The Load Sheet use case calls `GET /load-sheets?deliveryDate=`. The print adapter is unchanged.

Views keep reading dictionaries. Domain use cases do not take a locale and do not compute totals.

## Rejected alternatives

### A `returns` module

Rejected. The screen opens the sale and calls the existing line and void use cases.

### A client-side week calculation used as the edit lock

Rejected. The client may format the week for display. The API rejects an edit outside the window. A local date would drift from the business timezone.

### Catalog admin screens in this feature

Rejected. PDR-002 puts Excel and Alegra on the API. This SPA does not import a workbook or call Alegra.

## Consequences

`sales-day`, `sales`, and `fulfillment-output` gain use cases and views. `src/app/` only routes to them. Shared HTTP stays the transport.
