# ADR-005 — Pedidos is its own feature module

**Status:** Proposed
**Date:** 2026-11-16
**Document role:** Architecture decision for [PDR-006](../pdrs/PDR-006.md). Not a description of the running UI.
**Depends on:** [ADR-001](./ADR-001.md). API shape: Core API [ADR-005](../../../prime-sweets-api/docs/adrs/ADR-005.md).

## Context

The purchase sheet is a different task from a wholesale sale or a retail day: another party (the supplier), another money column (cost), and a read-only last quantity. The sales module already owns customer, delivery date, and invoice. Folding Pedidos into `sales` or `retail-sales` would mix two write models in one view.

The API keeps line detail only on the latest order and serves last quantities on the supplier payload. The client must not recompute "last order" by paging historical orders.

## Decision

Add a feature module `purchasing` with the usual hexagon: domain models, use cases, HTTP adapters, and views.

| UI concern | Source |
|---|---|
| Supplier list, rename, linked products | `GET/POST/PATCH /suppliers`, `PUT /suppliers/:id/products` |
| Sheet rows, unit cost, last quantity | `GET /suppliers/:id` only |
| Typed quantity, note, line cost, order total before save | Client state. Line cost uses the unit cost from that payload. |
| Save | `POST /purchase-orders` with `productId`, `quantity`, optional `note` |
| Past orders | `GET /purchase-orders?supplierId=` headers; `GET /purchase-orders/:id` for the one that still has lines |

Product search for linking reuses the catalog search port. The sheet does not call search to build its rows.

Navigation gains one entry, **Pedidos**, in the same shell switch as the other sections (sidebar / bottom bar). No new breakpoint.

## Rejected alternatives

### A tab inside Productos

Rejected. Productos answers "what are my prices". Pedidos answers "what do I buy from this supplier". PDR-004's navigation rule is one section, one question.

### Deriving last quantity in the browser from the previous order payload

Rejected. The supplier sheet already includes it, and older orders have no lines. A client-side scan would be wrong as soon as the API compacts them.

## Consequences

- New routes under the shell, for example `/purchasing`, `/purchasing/:supplierId`, `/purchasing/:supplierId/order`.
- New i18n keys in Spanish and English.
- `architecture/`, `model/`, and `flows/` stay unchanged until the module is in the client. Implementation steps are [SPEC-006](../specs/SPEC-006.md).
