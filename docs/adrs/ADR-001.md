# ADR-001 — One SPA with hexagonal feature modules

**Status:** Proposed
**Date:** 2026-10-20
**Document role:** Architecture decision for the Version 1 UI. Binding design; not a C4 snapshot of the running app.
**Current runtime:** [docs/architecture](../architecture/README.md). The repository is a Vite SPA. Feature modules for identity, catalog, customers, sales day, sales, and fulfillment output are implemented.

## Context

Sellers will use one responsive web application on a phone and on a PC. The Core API already owns Sales Day, customers, catalog search, sales, Load Sheet generation, and invoice documents. Printing stays on the PC through the Windows print dialog.

The risk on the client is a screen that calls `fetch` directly, recalculates totals, or copies API payloads into components. That would create a second implementation of rules the API PDR already fixed.

## Decision

The UI is **one Vite + React + TypeScript single-page application**.

Business features are modules under `src/modules/<feature>/`, not global folders of components, hooks, and services. Each module uses hexagonal layering as defined in `.cursor/skills/frontend-hexagonal-ddd/`:

- `domain/` — client models and input checks, no React and no HTTP;
- `application/` — use cases and outbound ports;
- `adapters/ui/` — views, presentational components, and hooks;
- `adapters/infrastructure/` — HTTP implementations and DTO mappers.

The initial modules match the API contexts the seller touches:

- `catalog`
- `customers`
- `sales-day`
- `sales`
- `fulfillment-output`

`src/app/` is the composition root (router, container, styles). `src/shared/` holds the HTTP client, environment, and other technical code with no business aggregate inside it.

There is no second deployable "print service". Printing is an outbound adapter in `fulfillment-output` that calls the browser print dialog.

## Principles

1. **The API is authoritative.** A use case displays or submits. It does not allocate invoice numbers, group a Load Sheet, or recompute official totals.
2. **DTO mapping is explicit.** API JSON is mapped to a client model before it reaches a view. Components do not depend on raw response shapes.
3. **React stays at the edge.** Hooks load state and call use cases. Views render and emit events.
4. **Infrastructure is replaceable.** `fetch` and `window.print` can change without rewriting a use case.
5. **Responsive layout is presentation.** Phone-width and PC viewports reflow in UI adapters. They are not modules, routes, or a second client. The SPEC states the layout rules.
6. **Language is presentation.** Spanish and English are dictionaries at the UI edge. They are not a bounded context and they do not change API contracts.

## Dependency rule

```text
View / hook
      |
      v
Use case
      |
      v
Client model
      ^
      |
Outbound port
      ^
      |
HTTP or print adapter
```

## Rejected alternatives

### Technical folders only (`components/`, `hooks/`, `services/`)

Rejected because sale, customer, and invoice code would mix, and HTTP calls would land inside screens.

### Reimplementing business rules in the client for offline use

Rejected. Version 1 requires connectivity. Local checks are limited to input shape.

### A separate print application

Rejected. OQ-04 gives printing to this UI. A second app would split the same seller session.

## Consequences

Modules have more files than a single `pages/` tree. Sellers get one codebase for capture and print. Domain tests can run without a browser. Those modules are in the running shell.
